# Recipe Studio 0.6 kitchen pilot

The existing application now has a composer for pantry-only cooking, pantry plus 0–5 missing products, and inspiration without a pantry. Users choose a meal or full day, servings, time, equipment and temporary exclusions. The reference recipe library remains a secondary section. Studio and chat use the same pantry and topic-specific candidate IDs.

Food selection uses exact catalogue identities and visible preparation states. Russian free text proposes identities; ambiguous chicken needs raw/cooked clarification, frozen weights are not silently converted, and egg counts are not converted to grams. Unknown products need a verified label. An unspecified inventory mass means the quantity must be weighed before cooking. Pantry changes, saved recipes, favorites, ratings, accepted days and quantified diary entries require explicit revision-guarded confirmation. Viewing a recipe never consumes stock. Half a serving and half the whole batch are distinct actions with a calculated confirmation preview.

The server builds original combinations using 12 controlled method families. Sol high may choose known IDs and grams, with at most three candidates and 40 food records. It cannot supply nutrition, arbitrary instructions or code. Server validation checks schema, IDs, distinct ingredients, group bounds, required roles, inventory for the whole batch, exclusions, allergies, equipment and time. Canonical steps come from the server and nutrition from keto_core. Oil and salt are never implicit. Labels distinguish generated drafts from deterministic template fallbacks; neither has been kitchen tested. Cooking time is an estimate. Foodsafety.gov thermometry requirements are retained: poultry 74 °C, fish 63 °C, egg dishes 71 °C, casseroles and reheated leftovers 74 °C.

Daily planning uses confirmed saved targets and the existing deterministic energy, protein, carbohydrate, fiber and saturated-fat checks. A bounded portion search revalidates rounded ingredient quantities and stock across all three meals and all servings. Infeasible results remain partial and cannot be accepted. Targets are not weakened. Unknown nutrients remain null; a daily product-policy pass is not clinical or complete micronutrient approval. A single meal's equal share of the remaining daily carbohydrate allowance is labelled as a product assumption, using confirmed quantified diary records only.

Confirmed preferences are shared across topics in the existing personal document and core settings. Forgetting removes the fact and exclusions introduced by it, preserves unrelated restrictions and invalidates cached kitchen candidates. Topic deletion removes its own quotes and candidates without deleting shared health facts. Personal JSON exports include kitchen fields and topics; deletion of the existing document includes all new fields. The membership administrator cannot read another member's pantry, diary or recipe memory.

Retrieval uses at most five own historical quotes, each at most 500 characters, plus the current eight messages. Matching is bounded keyword/stem matching, without an external semantic service. Historical preference/medical statements are not extracted as canonical memory. Quotes are explicitly untrusted. Public guidance retrieval is separate from food numbers and excludes retracted material. Private imported sources cannot modify health memory, safety policy or model routing.

Generation uses the existing signed stateless Azure bridge, D1 CAS, session/consent checks and request idempotency. User and global request quotas reserve before paid generation; replay does not make another paid call, and changed payloads with the same ID fail. Revoked consent or expired sessions discard results. Explicit kitchen controls need no Terra call. Other intent recognition may use one Terra followed by at most one Sol call within the remaining shared time budget; role usage is added rather than overwritten. Missing configuration fails closed into an honestly labelled template fallback, without a public OpenAI key or automatic provider cascade.

The versioned policy is `service/data/kitchen_policy.json`. It defines Belarus defaults, aliases, method roles, substitutions, limits and repetition weights. There are no new dependencies, D1 migrations, cloud resources or beta memory services. Source work is versioned 0.6.0-kitchen-pilot; the existing Azure plugin retains its identity.

Validation here is local and synthetic. Parent must perform a real full-schema Sol call, target-runtime validation, isolated visual checks at 375/440/1280 px and deployment acceptance. Google sign-in, voice, physical devices and clinical suitability are not established by these tests. This phase performed no browser use, cloud mutation, commits or publication. Exact checks and limitations are in `qa/KITCHEN_IMPLEMENTATION_RESULT.json`.
