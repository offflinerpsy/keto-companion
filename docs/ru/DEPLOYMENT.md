# Выпуск: только по зафиксированному коммиту

1. Откройте отдельную GitHub Issue с задачей и критериями приёмки. Создайте ветку `release/...`. Проверьте `docs/CURRENT_STATUS.json`, действующие ресурсы и результаты тестов; не создавайте повторно D1/R2.
2. Зафиксируйте SHA коммита и `artifacts/files_manifest.json`. Выпускайте именно эти байты. В текущем этапе разрешён только staging, не production.
3. Сверьте применённые миграции с `schema_migrations`. Не повторяйте ALTER TABLE вслепую. Для staging используются отдельные D1 и R2, не производственные данные.
4. Загрузите `worker-modules.mjs` и перечисленные TEXT-модули через документированный Cloudflare multipart API. Имена модулей обязаны совпадать с импортами. Не добавляйте новый Wrangler-проект: текущая среда использует cf и API.
5. Настройте DB/UPLOADS и публичные параметры. `SESSION_HMAC_KEY` хранится только как secret binding. Вычислительный мост нельзя объявлять подключённым до отдельного реального теста HMAC/managed identity.
6. Проверьте версии, хеши выданных файлов, `/health`, `/auth/config`, отказ анонимным приватным маршрутам и настройки приватности R2. Запишите receipt без секретов, журнал проверки и ссылку на коммит. Завершите Issue и merge только после проверки.

Точная конфигурация: `cloudflare-saas/DEPLOYMENT_GUIDE_RU.md`. План staging: `deploy/cloudflare-staging.json`. Выпуск не означает успешного Google-входа конкретного человека, popup/voice проверки или клинической пригодности.

В случае ошибки остановитесь на проверенной контрольной точке. Не переключайте production и не откатывайте данные без отдельного плана. Откат кода не является откатом D1/R2. Условия реальной авторизации и согласия нельзя обходить тестовой учётной записью в production.
